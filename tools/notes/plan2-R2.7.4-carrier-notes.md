# R2.7.4 — the evaluator return-carrier: measurement + design notes

Plan: `~/FoxyLabs/tla-lus/R2.7.4-plan.md`. Handoff: `plan2-R2.7.4-handoff.md`.
Oracle pin `tlaplus@4ba7d8811289fb8e95dac4d5e554c05216ba3100`, unchanged.

## R2.7.4.0 — DONE 2026-08-25 (docs/oracle/probe only; no desk change)

Two questions were owed: **does `tlc-coverage` actually need the return-carrier**,
and **what shape does the carrier take against all three consumers**. Both answered
by measurement. The row's premise was wrong in the same direction R2.6.1's was.

### Headline

**The action-level coverage numbers are BFS-cursor quantities. Coverage does not
need the evaluator surgery.** Only the sub-expression lines do, and those are
outside the corpus's oracle projection today. `R2.7.4.1`'s consumers are therefore
the register store and the RNG — two, not three.

### What the pin's `-coverage` output actually is

Five line kinds, from `CostModelCreator.report()` + `ActionWrapper.report()`:

| line | EC | template | contents |
|---|---|---|---|
| `<x line 3, col 10 … >: 3` | 2779 `TLC_COVERAGE_VAR` | `<%1% %2%>: %3%` | per-VARIABLE distinct-value count |
| `<Init …>: A:B` | 2773 `TLC_COVERAGE_INIT` | `%1%: %2%:%3%` | `A = getEvalCount()`, `B = A + secondary` |
| `<Act …>: A:B` | 2772 `TLC_COVERAGE_NEXT` | `%1%: %2%:%3%` | `A = secondary`, `B = getEvalCount()` |
| `<Cons …>: A:B` | 2778 `TLC_COVERAGE_CONSTRAINT` | `%1%: %2%:%3%` | `A = secondary`, `B = eval + secondary` |
| `  line …: N` / `  |line …: N[:M]` | 2221 / 2775 | `  %1%: %2%[:%3%]` | per-NODE eval counts (and cost) |

`SafetyDump.java:130` projects **only INIT and NEXT, argument index 2** — i.e. the
`B` column: initial states found, and states generated per action.

### Where each counter is incremented (pin source)

- **NEXT primary** — `Worker.addElement` (`Worker.java:419`) `action.cm.incInvocations()`,
  once **per successor state generated by that action**, before any constraint or
  invariant filtering.
- **NEXT secondary** — `Worker.java:538` `incSecondary()`, only when the successor's
  fingerprint was **not already in the FPSet** (newly distinct).
- **INIT primary** — `Tool.getInitStates` (`Tool.java:529`, `:562`) per initial state
  added; **secondary** at `:553` when an all-assigned candidate fails a remaining
  conjunct (`processUnsatisfied`).
- **CONSTRAINT** — `Tool.isInModel` (`:2891`/`:2896`): primary when the constraint is
  FALSE, secondary when TRUE.
- **VAR** — `Worker.java:478` `odn.count(succState.lookup(name))`, only for successors
  that are `inModel && unseen` (i.e. actually enqueued), NEXT path only — initial
  states are never counted.

Every one of these is a count of **states at a checker boundary**. None of them is a
per-node evaluation count. The per-node counts are the 2221/2775 lines, which come
from `OpApplNodeWrapper` inside evaluation and are the only thing the carrier buys.

### The probes (`-workers 1`, all verified against the run's own statistics)

| probe | spec shape | measured | arithmetic check |
|---|---|---|---|
| P2 | `Inc == x<3 /\ x'=x+1` `\/` `Dec == x>0 /\ x'=x-1` | `Init 1:1`, `Inc 3:3`, `Dec 0:3` | 1+3+3 = 7 generated ✓, Inc+Dec distinct 3 = 4−1 ✓ |
| P3 | `\E d \in 1..2 : x'=(x+d)%4` | `Step 3:8` (one line, `(5 25 5 40)` suffix) | 1+8 = 9 generated ✓ |
| P4 | two actions, all successors already seen | `Same 0:2`, `Flip 0:2`, `Init 2:2` | 2+2+2 = 6 generated ✓, 0 new distinct ✓ |
| P5 | `CONSTRAINT x < 3` | `Up 2:3`, `Cons 3:4` | Up generated 3 incl. the constraint-dropped one ✓ |
| P6 | `(\E i \in 1..2 : Bump(i)) \/ Yup`, 2 vars | `Bump 2:12`, `Yup 3:6`, `x:3`, `y:2` | 1+12+6 = 19 generated ✓ |
| P7 | **two actions producing the SAME successors** | `A 2:2`, `B 0:2` | 1+2+2 = 5 generated ✓ |

Four findings that constrain the port's implementation:

1. **`getEvalCount()` counts STATES, not evaluations.** P2's `Inc` is evaluated from
   four states and scores 3 — the state where its guard fails contributes nothing.
2. **A successor dropped by CONSTRAINT still counts in the primary** (P5: `Up 2:3`
   with only 2 kept), and the CONSTRAINT gets its own line.
3. **Two actions generating the same successor are counted SEPARATELY** (P7: `A 2:2`,
   `B 0:2`), and the distinct-credit goes to whichever ran first, in action order.
   **This kills fingerprint-keyed attribution.** The port's `+edge-action-label`
   re-solves "the first getActions leaf whose relation reaches that fingerprint";
   that rule cannot produce `A 2 / B 2` — it would give `A 2 / B 0`. Coverage
   requires expanding **per action**, the way `Worker` does.
4. **`\E`-derived sub-actions collapse to ONE line.** `CostModelCreator` shares the
   `ActionWrapper` across actions with identical location, so P6's `Bump(1)`/`Bump(2)`
   report as one `Bump 2:12`. The port's `+get-actions` yields N `act`s (R2.4.6 proved
   N is right for simulation); coverage must **aggregate them by declaration location**.

### Two traps found while measuring

- **A run that prints a trace inflates every counter.** P7 under deadlock-checking
  reported `Init 3:3`, `A 2:6` — the trace re-solve re-invokes Init and the actions
  with coverage still recording. With `-deadlock` the same run gives `Init 1:1`,
  `A 2:2`. **Coverage corpus cases must be clean (`VERDICT ok`) runs**, or the
  re-solve work has to be reproduced exactly, which is a different and much worse
  problem. (The port re-solves for labels too, but not identically.)
- **The stdout channel is not stable enough to hash.** One early `-coverage 1` run of
  P2 produced a coverage block whose hash differed from its neighbours; it did not
  reproduce in 12 subsequent runs and the differing text was not retained, so the
  cause is unidentified — most likely a stray JVM line landing inside the block.
  The lesson is structural and holds either way: **keep coverage goldens on the
  `SafetyDump` path**, which reads `MPRecorder` records rather than stdout and cannot
  be corrupted by an interloping line. `gen-mc-tests.py` (which greps stdout through a
  DROP regex) is the wrong home for them.

### The `-coverage N` interval is not observable and must be refused by name

`TLCGlobals.coverageInterval` only gates *periodic* reporting; the end-of-run block is
identical for `-coverage 0`, `1` and `2` (9/9 byte-identical runs, timestamp line
excluded), because a corpus-sized run never reaches the interval. The interval is a
**wall-clock** behaviour, so it falls under the rule R2.6.1 applied to
`TLCGet("duration")`: no reproducible run may observe the wall clock. **The port takes
coverage as on/off and refuses the interval BY NAME** — not by silently accepting and
ignoring a number, which is exactly the silent option R2's acceptance forbids.

### The parity boundary for `tlc-coverage` (decision)

| surface | verdict | why |
|---|---|---|
| INIT + NEXT lines, both columns | **parity** target for R2.7.4.2 | BFS-cursor quantities; the port already has the action decomposition |
| CONSTRAINT line | **parity** target | `+bfs-step` already evaluates `cons`; it needs two counters |
| VAR line | **approved-difference**, tested | the count is a `CountDistinct.SyncedHyperLogLog(10)` ESTIMATE over `v.fingerPrint(FP64.New())`. Reproducing it needs bit-identical HLL registers *and* pins the run to `-fp 0`. It is an estimator, not a fact about the spec |
| sub-expression 2221/2775 lines | **approved-difference**, tested | per-node eval counts; the only consumer of the return-carrier, and unobservable to a caller reasoning about the spec |

Both differences are ABSENCES of lines the port never claims to emit, declared on the
wire and in `compatibility.md` — not wrong numbers. `SafetyDump`'s projection already
excludes both, so the corpus differential stays honest without being widened.

### Port-side facts R2.7.4.2 will need

- **There is no coverage option anywhere on the wire.** `check-opts` (`sur/tla-lus.hoon:161`)
  has `translate`/`view`/`difftrace`/`continue`/`cfg`/`mode`; `bfs-opts`
  (`lib/check.hoon:218`) has no counter fields. Both need one, plus the interval refusal.
- **`+bfs-step` expands the WHOLE relation at once** — `(next-states:ne st.vis next.o …)`
  at `lib/check.hoon:579`. Per-action expansion is needed for attribution (finding 3).
  Supporting evidence that this is safe: the `-generate` path already expands per action
  (`lib/check.hoon:1004`, `:1069`) and R2.4.6 verified its statistics against `-simulate`.
  The existing safety/mc goldens are the regression check that generation ORDER is
  unchanged; if it changes, the counters are not worth it and the row re-opens.
- **The coverage label is the DECLARATION span, not the body span.** `printLocation()`
  uses `action.getDeclaration()` — the `N_IdentLHS` subtree, so `Bump(i)` spans its
  parameters (P6: `line 5, col 1 to line 5, col 7`). Trace labels use the *body* span,
  which is what `+action-label` renders today. `sem-def.at` is `(span-of:ast u)`, the
  **whole definition**, so the declaration span is not currently stored — it is available
  at generation time from `+def-lhs` (`lib/semantic.hoon:2644`). Store it as a new
  non-recursive `sspan` field on `sem-def` (6 construction sites) or recompute from the CST.
- **The 1:N suffix**: when the action's `pred` location differs from the definition body's,
  the pin prints `<Name decl (bl bc el ec)>` with the *actual* disjunct's span (P3).

## The carrier (R2.7.4.1) — design, and the isolation probe

Consumers narrowed to two: the `TLCSet` register store and the RNG.

```
+$  rst  $:  regs=(map @ud value:v)   ::  TLCSet registers, worker-local
             es=@                     ::  java.util.Random state
         ==
+$  eout  [res=eres st=rst]
```

- **Carry on BOTH branches of `eres`, not inside `%&`.** A `TLCSet` write that precedes
  a *failing* conjunct is visible in the pin (it mutated a Java field) and would be lost
  if the carrier rode only the success branch. It matters where a failure is CAUGHT
  rather than fatal — `TLCExt!AssertError` (R2.6.3) is exactly that case. Carrying on
  both branches is correct there and harmless everywhere else; R2.7.4.3 should still
  measure the pin's behaviour before claiming parity for it.
- **`pst` is the precedent, and should be subsumed rather than duplicated.**
  `+$ pst [es=@ ls=@ ngen=@ud]` (`lib/node-eval.hoon`) already threads RNG state by `=^`
  through `+psolve`/`+next-states-prob` for `-generate`. Two seed channels would be a
  latent divergence; `.4` should make the simulation path read `es` from the carrier.
- **Signature policy**: keep `eval`, `eval-text`, `solve-init`, `solve-next`, `pred-bool`,
  `eval-module-def`, `eval-dbg`, `fp-of-text` as wrappers that default the carrier and
  discard it (≈100 test call sites stay untouched); add carrying variants for the
  checker's hot path.

**Isolation probe — PASSED** (`-build-file` on a scratch `lib/probe-rst.hoon`, ship
`~zod`, committed and then removed; the repo desk was never touched). A pair return type
mentioning `value` in both halves, threaded by `=^` through a recursive walk over
`value`, both **compiles and runs**:

```
> (walk:pr [%set %set-enum ~[[%int --1] [%seq ~[[%int --2]]]]] empty-rst:pr)
[res=[%.y p=[%set …]] st=[regs={} es=2 cov={}]]
> (put-reg:pr 0 [%int --42] empty-rst:pr)
[regs={[p=0 q=[%int p=--42]]} es=0 cov={}]
```

No `[skipped … frames]`, no `recover: dig: over`. This was worth doing: R2.7.2's failure
mode was a RUNTIME `dig: over`, not a compile error. The result is consistent with
R2.7.2's rule — `rst` adds no member to `value`'s recursion cycle; it only mentions it,
as `eenv` already does.

## R2.7.4.2a — per-action expansion — DONE 2026-08-25

`+bfs-step` now expands the next-state relation **per action, in `+get-actions`
order**, registering each action's successors as they are generated, instead of
solving the whole relation in one `+next-states` call. One arm changed
(`lib/check.hoon`); no mold, no wire, no output, no counters yet.

Why it had to come first: R2.7.4.0's finding 3 — two actions generating the same
successor are counted separately (`A 2:2`, `B 0:2`) — means coverage attribution
cannot be reconstructed after the fact from fingerprints. The counters have to be
incremented where the successor is produced, which requires this shape.

Three behaviours were preserved deliberately, each for a measured reason:

- **the `TLCGet` read point.** The environment is built once per dequeued state,
  before any of its actions run, so the statistics an action reads are those
  standing before the expansion — R2.6.1's measured read point, and what the
  `tlcget-stats` golden pins.
- **budget accounting.** `spent` still advances by the number of successors the
  dequeued state produced (now summed across actions), so the slice-boundary
  resume contract and `run-stats-full`'s budget-independence hold.
- **the out-degree sample.** Still one sample per DEQUEUED state (newly-distinct
  successors across all its actions), not one per action — `Worker.outDegree`
  samples per state.

One behaviour deliberately CHANGED, toward the pin: a violation found under an
earlier action now pre-empts evaluating a later one, where before the whole
relation was solved (and could raise an evaluation error) before anything was
registered. That is tlc2's order — `doNextCheckInvariants` throws out of the
worker loop before the remaining actions are evaluated. No golden moved, so the
distinction is not currently exercised by the corpus.

**Verified on the ship, all green, zero goldens moved:** `mc` (33), `trace`,
`inv-constraints`, `stats`, `fp`, `symmetry`, `safety-gen`, `dfid`, `job`,
`spec-decomp`, `liveness-verdict`, `neval-mc`, `sim-stats`, `fuzz`, **`tier2`**
(the real-world specs, which is the evidence that LET/INSTANCE/`\E`-decomposed
actions expand identically). `tier2-sub`, `sim` and `sim-live` also green.

## R2.7.4.2 is NOT carrier-free after all — one number needs R2.7.4.1

Measured while building the INIT line, and it corrects **my own R2.7.4.0 sizing**
(the pin facts in that section stand; what I got wrong was the port-side cost):

| probe | `Init ==` | line |
|---|---|---|
| PA | `x \in 0..3 /\ y = 0 /\ x > 1` | `Init 2:4` |
| PB | `x \in 0..3 /\ x > 1 /\ y = 0` | `Init 2:2` |

**The INIT secondary counts candidates rejected by a conjunct evaluated once the
state is ALREADY FULLY ASSIGNED** — `Tool.getInitStates`'s `ps.allAssigned()`
branch (`Tool.java:536-556`), which increments `cm.getRoot().incSecondary()` and
then calls `processUnsatisfied`. A rejection while a variable is still unassigned
(PB) increments nothing. The port's counting site is exactly `+solve-filter` when
`(complete part vars.e)` holds and `mode` is `%init`.

This matters because **`SafetyDump` projects INIT's argument 2, which is
`getEvalCount() + secondary`** — so even the corpus projection needs it. It is a
state-level counter, not a per-node one, but it lives inside the port's action
solver (`+solve` and its 19 `^-  sres` arms) and `sres` has no more channel for it
than `eres` does.

So the remainder of R2.7.4.2 — the INIT line, and with it the whole coverage block
— needs the return-carrier. **R2.7.4.1 should go next**, extended to cover the
SOLVER arms as well as the evaluator arms, and the INIT rejection count should be
a field on `rst` from the start. The alternative (a solver-only counter threaded
now, widened by `.1` later) is the same 19 arms touched twice.

NEXT and CONSTRAINT lines remain carrier-free: `Worker.addElement` /
`Worker:538` / `Tool.isInModel` all have port-side homes on the BFS cursor.

### What per-action expansion costs

A/B on the ship, same `mc` shard, same 33 cases, old file vs new file (each
deployed and run in turn; the per-arm timings the test runner prints, not
wall clock — a first attempt at wall-clock A/B was abandoned because whole-shard
times varied 30s-83s run to run on this ship and cannot resolve a small delta):

```
33 cases   old 43.866 ms   new 45.972 ms   delta +4.8%
worst rows: tlcget-stats +12%, tlcget-level +10%, live-box +17%, gate-trivial +15%
```

**+5% overall, up to ~15% on small search-heavy runs**, paid on every run whether
or not coverage is on. Two causes, one of which is removable:

1. N solver entries per state instead of one. This is inherent, and it is also
   what tlc2 does unconditionally — its worker loop calls
   `Tool.getNextStates(action, ...)` per action regardless of coverage — so the
   port's whole-relation solve was the divergence, not this. Keep it.
2. `+get-actions` is rebuilt once per `+bfs-step` invocation. For a small run
   that is a fixed cost against a short search, which is why `gate-trivial` and
   `live-box` move most. **Removable**: the callers that render traces already
   compute the same list (`+safety-run`, `+do-explore`), so `.2b` should carry
   `acts` on `bfs-opts` — the same field change it needs anyway for the root
   action name — and pass it in rather than rebuilding it.

## R2.7.4.1a — the SOLVER carrier — DONE 2026-08-25

`+$ rst` (registers + RNG seed + the INIT rejection count) and `+$ sout [sres rst]`
now exist in `lib/node-eval.hoon`, and the whole action solver carries them:
`+solve`, `+solve-filter`, `+solve-letin`, `+solve-conj`, `+solve-each`,
`+solve-disj`, `+solve-ite`, `+solve-exists`, `+solve-forall`,
`+solve-unchanged`, plus the new `+init-states-rs` / `+next-states-rs`.

Nothing writes to it yet, so behaviour is unchanged by construction. The public
entry points keep their signatures as **carrier-discarding wrappers** —
`+init-states`, `+next-states`, `+solve-init`, `+solve-next`, `+eval-enabled` —
which is the signature policy the plan set, and it kept ~100 test call sites and
every `check`/`job`/`liveness` site untouched. One external direct caller of
`+solve` (`lib/liveness.hoon:345`, the `ENABLED <A>_e` test) was updated in place.

**This unblocks R2.7.4.2b**: `irej` is on `rst`, so the INIT coverage line's
`secondary` now has a channel out of the solver.

### The trap that cost the first two compiles: faces on the carrier pair

`+$ sout [res=sres st=rst]` compiles, but every `=^ r rs (solve ...)` that binds
from it produces `-find.p.r` at the next use. The face on the head leaks into the
bound variable, so `p.r` looks for `p` inside `res=…` and does not find it. The
`-generate` path had the answer already: `+psolve` returns a bare `[pres pst]`
with no faces, and its `=^ res p (psolve …)` + `?=(%none -.res)` narrowing works.

**Both carrier pairs are unfaced** for that reason. Do not add faces to them.

## R2.7.4.1b — the EVALUATOR carrier — STARTED, dispatch layer only

The evaluator is 47 arms returning `^- eres`, and every one of them has to carry
`rst` before `TLCSet` (R2.7.4.3) or `RandomElement` (R2.7.4.4) can work. That is
too large to land as one edit, so it is being done as an **incremental split that
keeps the tree green at every step**:

- `+eval-rs` is the carrying evaluator; **`+eval` is now the discarding wrapper**
  (`-:(eval-rs n e empty-rst)`), so no unconverted arm and no test call site had
  to change.
- Each batch converts one layer to an `-rs` arm; anything not yet converted is
  called from the carrying layer wrapped as `[(legacy-arm …) rs]`, which is
  correct precisely because nothing writes to `rst` yet.

**Landed so far:** `+eval-rs` and `+eval-apply-rs` (the dispatch layer). Everything
below them — `+eval-builtin`, `+eval-user`, `+apply-const`, `+eval-args`,
`+eval-bool`, and the ~40 builtin evaluators — is still wrapped.

**Remaining, in the order they should be converted** (each batch compiles and runs
the touched shards):

1. `+eval-args`, `+eval-bool`, `+eval-domain` — the helpers every builtin uses.
2. `+apply-const`, `+eval-user`, `+apply-def`, `+eval-letin` — application.
3. `+eval-builtin`'s switch and its ~40 leaf arms.
4. `+eval-node-op` and the `@Evaluation` overrides (`+eval-tlc-get`,
   `+eval-tlc-eval`, `+eval-assert-error`, `+eval-tlc-cache`, `+eval-tlc-defer`),
   which is where `TLCSet` and the RNG will actually write.
5. `+eval-enabled` and the solver's own `+eval`/`+eval-bool`/`+eval-domain` call
   sites, which today discard — ENABLED is the one place where discarding is a
   real (if narrow) difference once writes exist.
6. Unify `pst.es` with `rst.es` on the `-generate` path, so there is one RNG
   channel rather than two.
