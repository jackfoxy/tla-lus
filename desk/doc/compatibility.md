# Compatibility Notes

Intentional differences between `%tla-lus` and the pinned Java TLA+
toolchain (SANY / PlusCal / TLC). Each entry states the difference and why
it exists. Differential tests use normalized oracle output; anything listed
here is a deliberate, documented divergence rather than a latent bug.

The desk contains **no** GUI, Toolbox, `tla2tex`, or Java code or
dependencies; the Java `tla2tools.jar` is used only to build the differential
goldens and is never shipped or called at runtime. The only vendored upstream
text is the MIT `StandardModules` (`lib/stdmods.hoon`, with its provenance
header).

The scaffold gate proves hygiene, **not** Java parity. It is worth being exact
about what each artifact does and does not claim:

- the **ledger** is now closed — every one of its 125 rows is `parity`,
  `approved-difference`, `replaced` or `excluded`, with none `partial`,
  `absent` or `oracle-only`;
- a `parity` row means a differential comparator agrees with the pin on that
  row's projection, not that every conceivable behaviour was compared;
- an **`approved-difference`** row means the port deliberately differs and the
  difference is stated and tested. All thirteen are enumerated below — this
  document has no prose-only claim of a difference that the matrix omits, and
  `tools/check-portmap.py` fails if a new one is added to the ledger without
  appearing here.

## Unit P2-2 — Lexer/parser diagnostic parity

The parser reproduces SANY's `TLAplusParser.parse()` error text byte-for-byte
on the differential corpus (`gen-parse-err-tests`: every syntax-corpus REJECT
case plus hand-written malformed modules; oracle
`tools/oracle/ParseErrDump.java` captures the verbatim `PErrors` entries):

- The `***Parse Error***` block: the optional `Was expecting "…"` line (the
  grammar's `expecting` state), the JavaCC `Encountered "…" at line L, column
  C and token "…"` line (raw upcoming-token echo incl. the synthetic
  `Beginning of definition` token belchDEF splices, `<EOF>`, and the
  `add_escapes`-escaped current token), and the `Residual stack trace` of the
  top five `bpa` production entries with their entry positions.
- OperatorStack's thrown messages (precedence conflict, illegal combination,
  the mistyped-`==` hint, missing expression/operator, postfix/prefix/infix
  encounter errors, `.`-reduction errors), `finalReduce`'s unwrapped
  `Couldn't properly parse expression` push followed by the wrapped
  ` Couldn't reduce expression stack.` exception, junction-indent errors
  (`Item at <loc> is not properly indented …`), label
  (`Removing label at <loc> would change expression parsing.`), `\X`-as-infix
  rejection, `@ used in !.@`, and fairness-subscript failures.
- Lexical errors pass through the byte-exact `TokenMgrError` text (unit 3),
  wrapped as `Lexical {error: EOF reached, possibly open comment starting
  around line N` when the failing lexeme spans lines, exactly as `parse()`
  does.
- `+parse-typed` exposes the typed result `[tree diags fatal]`; the job
  engine's `%parse` stage emits these diagnostics as events, so a rejected
  submission carries SANY's exact error text on the wire.

The `expecting` state and residual-stack production frames are now ported for
every grammar area the extended corpus exercises — R1.3.5.6.1–.5 swept
expression/control-flow, collections + EXCEPT, temporal/fairness, LAMBDA,
module-level, and proof/theorem productions to byte-exact `Was expecting`
strings and `bpa` stack entries (see `parity-manifest.md` `parse-errors` =
`parity`).

Approved differences and residues (tracked in `parity-manifest.md`):

- **Module-body LOOKAHEAD recovery points (approved difference).** SANY's
  module body uses JavaCC syntactic LOOKAHEAD to decide whether a unit starts;
  when a would-be unit fails to parse as a whole, SANY rejects it *before*
  entering the production and unwinds to the module-body choice, reporting
  `Was expecting "==== or more Module body"` at an arbitrary recovery point
  (the module header token). The port instead parses the unit greedily and
  reports the **precise** failure point. Measured cases: `f[x \in S] ==` /
  `g[x \in S, y \in T] ==` (SANY: `Encountered "f" … token "----"`, stack just
  `Module definition`; port: empty-RHS `Encountered "===="` with the full
  Definition stack), `RECURSIVE f(` (SANY multi-token echo `( ====` @ the `(`;
  port: `Identifier, _ or prefix op` inside `Constant declaration items`),
  `x == f(`, `x == [a]_v v`, and the empty definition RHS `x ==`. The port's
  message is strictly more precise; reproducing SANY's unwind would require
  full-unit backtracking at the module-body level to emit a *less* useful
  error. Verdict-level parity is unaffected (both REJECT).
- Diagnostics carry the message and fatality but `at` spans are not yet
  populated (`(unit loc)` stays `~`); the message text embeds the positions.
- Error recovery is otherwise fail-fast: SANY accumulates multiple `PErrors`
  entries only via non-throwing pushes (`finalReduce`, fairness, `!.@`), which
  is reproduced; JavaCC-level resynchronization does not exist in either
  implementation.

## Unit 6 — Semantic graph construction

The differential oracle is a normalized semantic tree (`tools/oracle/SemDump.java`),
not raw `XMLExporter` XML. Two fields present in the XML are intentionally
omitted from the normalized form:

- **Volatile UIDs** — SANY assigns global sequential node IDs that depend on

## Unit P2-7 — TLC output (EC/MP) parity

`lib/diagnostics.hoon` ports `tlc2.output.MP.getMessage` byte-for-byte over the
**reachable EC set** — every error/warning code the ported config + semantic +
safety + liveness engine can emit (TLC `2104`/`2105`/`2107`/`2110`/`2116`/`2222`/
`2227`–`2233`/`2237`/`2257`/`2259`/`2272`/`2279`/`2281` and CFG `5001`–`5006`):

- `+ec-body` is the `getMessage0` per-code template switch (`%N%` placeholders,
  arity-dependent branches for `2116`/`2228`); `+mp-subst`/`+mp-replace` reproduce
  `MP.replaceString` (replace `%<i>%` with the i-th parameter, ascending).
- `+mp-message [class code params tool]` wraps the body: `-tool` renders the
  `@!@!@STARTMSG <code>:<class> @!@!@` / body / `@!@!@ENDMSG <code> @!@!@` machine
  frame; non-tool renders the class prefix (`Error: `/`Warning: `/…) plus, for a
  WARNING, the `\n(Use the -nowarning option to disable this warning.)` hint.
- The message **class** per code (`ERROR`=1, `WARNING`=3) is taken from the Java
  `printError`/`printWarning` call sites.
- The oracle is `tools/oracle/MPDump.java` (dumps `getMessage` in both modes from
  the pinned jar); `tools/gen-mp-tests.py` drives 112 differential cases.

EC codes surface as typed `diagnostic` nouns — `[[%tlc code] severity stage
message …]`, emitted by `config.hoon` (CFG family), `assume-fail` (`2104`/`2105`),
and the `check.hoon` verdict path — whose `message` holds the MP body. `+diag-render
[diagnostic tool]` serializes any such noun to its plain or `-tool` MP line on
demand; `config.hoon`'s CFG diagnostics route their body through the same `+ec-body`,
so there is a single MP source of truth.

**Approved difference — the CLI `-tool` stream.** `tlc2.TLC -tool` emits a stdout
stream that interleaves STARTMSG/ENDMSG-wrapped `MP.getMessage` calls with raw
state/statistics lines, for the Toolbox to parse. The port is a Gall agent: its
machine-readable contract is the typed `diagnostic` **event** (structurally richer
than the `@!@!@` text), so no run mode threads that stdout stream — nothing would
consume it. Every individual message's exact `-tool` bytes remain reproducible via
`+diag-render`/`+mp-message` (proven by the 112-case differential); only the
whole-run stdout interleaving is out of scope.

## Unit 7 — Level checking

Levels (0 constant / 1 state / 2 action / 3 temporal) are now computed and
emitted (`L<level>` on every node) and match SANY across the corpus,
including the cross-definition `spec` case. Two behaviors to note:

- **Unreferenced formal parameters keep level `-1`.** SANY never level-checks
  a formal parameter that the body does not use, so its level stays at the
  uninitialized sentinel `-1` (e.g. `b` in `Foo(a, b) == a`). This is
  reproduced exactly rather than normalized to 0.

The plan-2 unit-4 increment ports the constraint machinery and
diagnostics. Subunits 4.1–4.6 are at parity: the level/arg-level
constraint sets with SANY's min/max merge direction and the full sorted
LEVELS projection (levels, max-levels/weights, higher-order
min-max/opLevelCond, level params, level/arg-level constraints,
arg-level params, allParams, non-Leibniz params); bottom-up levels with
the unreferenced-binder `-1` sentinel and escaped DIAGS text; the
higher-order rules (4272/4273, the call-site argLevelParam remapping,
alp-driven constraint bounds, the doubly-higher-order non-Leibniz rule,
and the 4270/4271 arity mismatches); recursive fixpoint checking
(self/mutual/higher-order recursion, recursive functions, 4290); the
node-specific rules (4205/4206 and temporal 4310–4315, all boundary
cases); and instance/substitution (4244/4245/4246/4247, getSubLCSet
constraint contributions, operator substitutions as `$OpArg`, APSubstIn
theorem import, constructSubst ordering, and a pure `validate-target`
configuration gate). `Linter.java` record lint (4802) is also present.
Two-phase gating is normative: SANY runs level checking only when
semantic generation produced no errors (any semantic error renders every
level `-1`), while a level-check error leaves computed levels visible and
only adds `D`-line diagnostics.

Record-constructor linting (4.7) is at parity: the 4802 field-name
collision rule with its built-from-declarations suppression, nested and
multi-field constructors, and the driver-level `lint-options` (per-code
suppression, warning-to-error elevation, and the suppressed/as-errors
overlap rejection) matching SANY's `filterVisibleMessages`/
`reportMessages`. Because those controls are report-time and invisible
to the `Errors` channel, their evidence is Hoon unit tests
(`tests/lib/lvl`) rather than SemDump goldens.

Unit 4 is complete. The `%analyze` request runs the real Work Unit 3+4
pipeline (4.8): a `%semantic` stage calls `analyze-graph`, splitting the
diagnostics by phase and gating them exactly as SANY does (a semantic
error suppresses level and lint; a level error suppresses lint). The
`semantic`/`level`/`lint` flags select which phases' diagnostics are
emitted; `apply-lint-options` threads the driver warning controls. The
stage runs in a single bounded slice — a module bundle's analysis is
bounded like a capped exploration — so no mid-stage cursor is needed;
pause/resume is identical at every boundary. Cross-module instance
diagnostics carry the root module name as their loc source (the true
origin module is a deferred refinement, like the parser's typed-at
spans), and a request-carried `lint-options` set is a future sur
extension (the pipeline applies empty options today).

Remaining unit-4 residue:

- **BY/QED proof-step level rules** ride in when the proof-step nodes
  land (unit-3 residue).

## Unit 9 — Constant evaluation

Constant TLA+ expressions evaluate to canonical values matching the TLC REPL
(`tlc2.REPL`) across the corpus. One deliberate divergence:

- **String ordering.** TLC orders `StringValue`s by their internal
  `UniqueString` id; this port orders lexicographically. The divergence was
  measured and approved at subunit C1.7 — see *Unit 6C (C1.7) — string and
  model-value order* below for the evidence, the full consequence list, and
  what a result can and cannot be read to mean.

Not yet ported (later unit-9 increments): `.cfg` config parsing (keywords,
constant/model-value assignments, `SPECIFICATION`/`INIT`/`NEXT`, invariants,
properties, constraints, symmetry), model values, the StandardModule Hoon
override contract beyond the operators exercised, fingerprints, and full
lazy/enumerable value semantics for large sets.

Deferred to a later unit-6 increment (tracked here, targeted well-formed
modules only for now):

- **Semantic error recovery.** For ill-formed input (undefined operator
  reference, duplicate top-level symbol, arity mismatch) SANY does *not* fail:
  it builds a partial `ModuleNode` with `nullODN` sentinel operators, keeps the
  first of a duplicated definition, and records the problem on a separate
  diagnostic channel. The current port targets well-formed modules and does not
  yet reproduce these partial trees or emit the semantic diagnostics.
- ~~**EXCEPT** (`$Except` / `$Seq` index nesting) and **N_SetOfRcds**~~ —
  landed in P2-3 increment 3a (below). **INSTANCE / substitution** semantics
  (`$SubstIn`, `APSubstIn`), proof/theorem/assume expression bodies, and
  subexpression `!`-navigation are not yet translated into the semantic
  graph (they parse correctly at unit 4).

## Unit 6C (C1.7) — string and model-value order (family 5)

`StringValue.compareTo` and `ModelValue.compareTo` in tlc2 compare the
`UniqueString` **tok**: the position at which the string was first interned
during that run. `ModelValue.fingerPrint` folds the tok as well. This port has
no intern table — strings are atoms — and orders **lexicographically**.

**The measurement** (`tools/oracle/InternDump.java`, evidence regenerated into
`desk/test-data/stdops/intern-order.txt`):

- The intern table starts empty; SANY then interns **399 strings** for a
  10-line fixture before the module's own lexemes are reached — 112
  syntax-tree kind names (`N_*`), 49 internal operator names and sentinels
  (`$…`, `nullODN`, `LAMBDA`), and the builtin operator table — and the TLC
  phase adds 12 more (`beginLine`, `_action`, the config's model values, …).
- Each driver is deterministic, **but different drivers disagree**. The same
  fixture, same jar, same JVM: a `FastTool` alone renders `Longer` as
  `{"aa", "ab", "b", "z"}`, while SANY-then-`FastTool` renders
  `{"ab", "b", "z", "aa"}` — and `CHOOSE x \in MS : TRUE` returns `zz` under
  the first driver and `aa` under the second.

So the order is a property of the *run*, not of the specification.
Reproducing it would mean mirroring every interning call site inside SANY and
TLC **and** fixing which Java entry point runs — a permanent coupling to
tool-internal execution order, for behavior TLA+ itself does not define.
The divergence is therefore approved, and this port's order is the same on
every run, machine, and pipeline.

**What differs**, all fixed by `tests/lib/strorder`:

| surface | tlc2 | here |
|---|---|---|
| element order of a string set | interning order (`{"bb", "a", "ab"}`) | lexicographic (`{"a", "ab", "bb"}`) |
| `CHOOSE` over a string or model-value set | the first interned element | the lexicographically smallest |
| record field order in a rendering, and `DOMAIN` of a record | interning order | lexicographic |
| element order of a model-value set | interning/config order | lexicographic |
| `SortSeq` with a comparator over strings | follows `compareTo` | follows the lexicographic order |
| `ModelValue.fingerPrint` | folds the tok | folds the name (injective, not byte-identical) |
| symmetry orbit representative | lex-smallest by `compareTo` | lex-smallest by this port's total value order |

**What does not differ**: membership, equality, cardinality, deduplication,
and every verdict that does not depend on *which* element of an unordered set
is looked at first. Distinct-state counts under symmetry match, because the
orbit is the same set however its representative is chosen — only the stored
representative's fingerprint bytes may differ.

**What a result means.** A trace, a counterexample, or a rendered value from
this port lists set elements in lexicographic order; TLC would list the same
elements in its own run-dependent order. Where a spec's *outcome* depends on
which element `CHOOSE` picks from a string or model-value set, the two tools
may report different witnesses — as two TLC drivers already do — and neither
answer is more correct: TLA+ leaves it unspecified.

### Release R1.3 — front-end parity edges

Release-R1 sub-unit R1.3 drives the SANY front-end census (adversarial
`suite/`/`coverage/` conformance specs) to agreement. R1.3.1 put **LAMBDA**
op-args in the graph; R1.3.2 closed the **higher-order operator-argument**
edges (deep-4271 first-order check, infix/prefix/postfix operator constants
`_++_`, built-in operators `+`/`\cup` as op-args). R1.3.3 added the
**INSTANCE and quantifier/parameter** edges:

- **Parametrized instances** `I(x) == INSTANCE M` — the instance's own params
  are in scope for the `WITH` expressions and are **prepended** to every
  imported definition (arity grows, `parg`/`weights` follow); higher-order
  instance params `Inst(F(_,_))` bind at their arity.
- **Nested instance members** `M!Op(..)` (an instance inside the instanced
  module) resolve under the fully-qualified name.
- **RECURSIVE** operators substituted through `INSTANCE..WITH` (`A <- g`) and
  reached via a member (`foo(n)!Use`) ride the existing `$OpArg` path.
- **Tuple-pattern binders** `<<y, z>> \in S` bind each identifier
  individually, in both quantifiers and function definitions.
- **Operator-symbol parameters** in a definition, `TempTest(_+_)` /

## Unit P2-1 — Resumable job kernel (supersedes the unit-13 stub engine)

The job engine (`lib/job`) is now a budgeted continuation kernel: one
Gall event spends at most `default-budget` work units (states registered or
generated, transitions, or modules parsed) and persists a versioned, jammed
continuation (`$kont %1`) inside the `%2` job noun. Pause/resume at **every**
slice boundary is tested to produce an identical event stream and final job.
Consequences:

- **No stub stages exist.** The former placeholder `%parse`, `%semantic`,
  `%level`, `%lint`, `%translate`, `%explore`, `%simulate`, and `%terminal`
  stub bodies are gone. Every operation either runs the real pipeline or is
  rejected by type at submit (`+validate`) naming the unsupported behavior
  and its plan unit. A request can no longer finish `%ok` without the named
  work having run.
- **Per-event slicing.** The safety search, liveness graph build, liveness
  property scan, and seeded simulation all run behind persisted cursors
  (`bfs-cursor`, `sim-cursor` in `lib/check`). The simulation cursor
  saves the raw RNG sample, so slicing cannot change the random choices.
  Two enumeration atoms remain un-sliceable until B5's enumeration cursors:
  solving the Init predicate (one `+gen` call at `%config`) and generating
  one state's successors (one `+gen` call per queue entry).
- **Limits at the point of growth.** `max-states` and `max-depth` are
  checked as each state registers inside the search; `max-time` is checked
  against the submit time on entry to every slice; `max-artifact` before
  storing the report; `max-source`/`max-modules` at validate. All six
  request limits are now enforced (`max-time` previously was not).
- **State `%2` migration.** Terminal `%1` jobs carry over verbatim; active
  `%1` jobs ran the stub pipeline and cannot resume honestly, so they
  terminate `%failed 'restarted: the stub pipeline was superseded;
  resubmit'`.
- **Real artifacts.** A finished check stores a TLC-style `%report` text and,
  on violation, a typed `%trace` artifact (`%safety`, `%lasso` with
  `loop-start`, or `%simulate`). The stub translation/cfg artifacts are gone.
- **Simulation mode is live.** `%check` with `mode=%simulate` runs the real
  property-tested seeded engine (unit 12) through the kernel. Its `run-stats`
  map differently: `generated` = transitions taken, `depth` = deepest
  transition index; `distinct`/`queued` stay 0.

Still absent after P2-1 (tracked in `parity-manifest.md`): PlusCal
translation and translate-before-check (typed-rejected). (The `%analyze`
semantic/level/lint flags run the real pipeline — unit 4.8. Clay sources,
multi-module resolution inside `%check`, canonicalized search roots,
content-hash caching, quotas, and artifact retention all landed in unit
10 — see below.)

## Unit P2-10 — Gall + Clay integration

### 10.1 Asynchronous source load — at parity for the load itself

A `%clay` source bundle is no longer typed-rejected. It plans an extra
`%modules` stage that closes the module graph over **asynchronous** reads:
no stage touches Clay, so the kernel stays pure and resumable across the
network boundary.

- `step-result` gained `%await`: a stage returns the `read-request`s it
  needs and pauses. The agent performs them and resumes the job with
  `+deliver`; a paused job schedules no work.
- The `%load` cursor is a BFS over `EXTENDS`/`INSTANCE` references in
  appearance order, identical to `lib/modules` `+resolve`: user files
  shadow the standard modules (the read is attempted first, and only a
  name absent from every search root falls back to the vendored set),
  inner modules are registered from their outer file and never read, and
  search roots are tried in order (`SimpleFilenameToStream`).
- Module names map to the lowercased `<name>.tla` file
  (`util.FilenameToStream`); the case-sensitive declared-name check is
  preserved.
- Missing file, unparsable module, declared-name mismatch, and a missing
  config are typed `%modules` diagnostics (`[%lus 401]`) carrying the text
  the inline resolver reports for the same condition, then `%failed`.
- `max-source`/`max-modules` are enforced as bytes and files *arrive*, not
  only at submit → `%limited %source` / `%limited %modules`.
- A per-slice `load-budget` (8 reads) bounds a wide dependency fan-out
  independently of the work budget.
- The revision is **pinned at submit**: the agent resolves the requested
  case to a concrete aeon (`%cw`), so a commit mid-run cannot split the
  source set and no read can block on an unsettled case.
- Because a Clay run cannot know its config before reading it, `%config`
  appends the `%liveness` stage (and grows the progress total) when the
  loaded config names a `PROPERTY`.

The measured contract is equality with the inline path: a Clay run reaches
the same module graph, verdict, and statistics as an inline bundle of the
same files (`tests/lib/clay-load`, 17 cases; verified live on a fake ship
against `test-data/clay/multi` → `[%ok [5 4 0 4]]`).

Deferred out of this subunit at the time it landed, **each since closed by
its own section below** — 10.2 (path canonicalization and escape prevention),
10.3 (revision and content identity), 10.4 (quotas, retention, noun size),
10.5 (idempotency and delivery robustness), 10.6 (API versioning and state
migration). §10.7 is the measured close.

> 10.2-10.6 as owed, long after each had landed, and it is where the
> `src-clay-async-load` ledger row's stale residue text had been copied from.
> Both are fixed together.

Known deviations recorded now:

- A standard-module name is *read for* before falling back to the vendored
  text (the plan suggested skipping the read). Attempting it is what makes
  a user file shadow a standard module, matching the inline resolver.
- The load stage parses each module to extract its references and throws
  that tree away; `%parse` re-parses the root. The content-hash cache that
  removes the second parse is 10.3.
- A job paused on Clay has no watchdog: if a `%writ` never arrives the job
  stays active. Reads are answered synchronously when the path does not
  exist, and the pinned (settled) case makes an unanswered read a Clay
  bug, but no timer forces the issue.

### 10.2 Path canonicalization and escape prevention — at parity

`lib/source-path` is the **only** constructor of a `source-ref`, so a Clay
read cannot be named except through the guard.

- **Segments**: empty, `.`/`..`, `$`-prefixed, dotted, and non-knot
  (e.g. uppercase) segments are typed errors naming the segment and the
  path it appeared in.
- **Roots**: every candidate — the config included — must lie under a
  declared search root. Declaring `/` legitimately scopes the whole desk.
- **Pinned revision**: `+read-ref` refuses a `%da`/`%tas` case outright, so
  the revision the agent pinned at submit governs every read of the run and
  no read can block on an unsettled case.
- **Name mapping** is `util.FilenameToStream`'s and is exact: a module name
  becomes the lowercased name plus `.tla` under each search root, tried in
  order. The case-sensitive declared-name check stays with the resolver.
- Judged twice: the whole bundle (desk, root module name, search roots,
  config path) at submit, before a job exists; and each path again as it is
  turned into a read.

Clay is not a POSIX filesystem — a `..` segment is a malformed knot, not a
traversal, and a read is already confined to one desk. The guard is
therefore defense in depth plus an honest diagnostic: a malformed path is
named rather than silently missing.

Representation-agnostic sources (task 4): diagnostics and spans key on the
module name for both `%inline` and `%clay` runs, and an unparsable module
now reaches `%parse` on both paths, so SANY's own parse-error text is the
verdict either way (the loader registers the text as it arrived and simply
contributes no references). Two Clay diagnostics remain *better* than the
inline path rather than identical, which is an approved difference:

| Condition | Inline | Clay |
|---|---|---|
| referenced module absent | `module resolution failed` / `semantic graph generation failed` (downstream) | `Cannot find source file for module X imported in module Y.` at `%modules` |
| declared name ≠ file name | same downstream failure | `File name 'X' does not match the name 'Y' …` at `%modules` |

### 10.3 Revision and content identity — at parity

A run records what it read. Every module and the config carry a
`[source-id hash]` — the frozen wire id (`%inline name` or
`%clay ship desk case path`) plus the `shax` of the content — and the pair
is rendered into a **`%sources` artifact**, stored as soon as the sources
are known (at the close of the Clay load, or on entry to `%parse` for an
inline bundle) so a run that later fails still says what it read:

```
root spec
module helper 0x…  /~zod/tla-lus/268/test-data/clay/multi/helper/tla
module spec 0x…    /~zod/tla-lus/268/test-data/clay/multi/spec/tla
config 0x…         /~zod/tla-lus/268/test-data/clay/multi/cfg/txt
```

Modules are listed by name, so the record is deterministic and an inline
run's hashes are directly comparable to a Clay run's — only the id column
differs.

- **One revision governs a run.** The case pinned at submit is used for
  every read; a commit mid-run cannot split the source set. The whole read
  stream of a run is asserted to carry one ship, desk, and revision.
- **The parse cache keys on content**, not on location, so the same text
  read from two files parses once and a cache hit can never cross content.
- `%config` now generates the semantic graph **once** and hands it to the
  config assembly, instead of building (and reparsing every module) twice.
- Provenance is engine metadata, not the caller's output: when it does not
  fit inside `max-artifact` it is dropped with a `[%lus 402]` **warning**
  rather than failing an otherwise sound run — but never silently.

Vendored standard modules are not listed: they are not read, and are fixed
by the desk revision. Remaining duplicate work, tracked as residue: the
load stage still parses each module once only to extract its references
and discards the tree, and `%parse` re-parses the root through
`parse-typed` (which is what produces SANY's diagnostics). Sharing those
trees needs a cache that survives across stages, which would put syntax
trees into the persisted continuation.

### 10.4 Quotas, retention, and noun size — at parity

A request's own `limits` bound one job; a new `gquota` bounds the ship, so
one caller cannot starve it with many small jobs or by never collecting
results. Engine configuration, like `default-budget` — not caller-visible.

| Bound | Default | Enforced |
|---|---|---|
| concurrent active jobs | 8 | at submit, typed rejection |
| retained artifact bytes | 8 MB | at submit (rejection) + reclaimed when a job finishes |
| in-flight source bytes | 4 MB | at submit, typed rejection |

Every figure is **derived from the jobs map** rather than carried as a
counter, so the accounting cannot drift from what is actually stored and a
deleted job frees its quota by construction. An active Clay job reserves
its declared `max-source` (it has not read its sources yet); an inline
bundle holds exactly the bytes it carries; a terminal job holds none.

Rejections name the resource:

| Message |
|---|
| `global limit: too many active jobs` |
| `global limit: retained artifact bytes; delete a result first` |
| `global limit: in-flight source bytes` |

**Retention.** Over the bound, the oldest terminal jobs (by submit time,
ties by id) give up their artifact *bodies* first. The job, its result, its
statistics, and its diagnostics stay, and a `[%lus 403]` warning is
recorded on the job — so an artifact scry that later misses is explained
rather than blank. Active jobs are never touched, and the terminal-gated
artifact scry is unchanged. Reclamation runs when a job finishes, not on
every slice.

**Per-request limits during the load** (10.1) are unchanged and already at
the growth point: source bytes and module count accrue as reads *arrive*,
not only at submit, so a growing set crosses into `%limited %source` /
`%limited %modules` mid-load.

**Noun size.** The Work Unit 7.7 bound on the jammed continuation is now a
shared predicate applied to the `%load` cursor as well, so a pathological
dependency fan-out cannot grow an unbounded jammed resolver state →
`%limited %noun`.

Known limits of this design, recorded rather than hidden:

- A global bound is reported through the frozen `limit-kind`/rejection
  text, so a caller sees *which resource*, not whether the bound was its
  own or the ship's. Distinguishing them needs a wire change.
- `retained-bytes` measures the jammed size of a job's artifact map, while
  the per-request `max-artifact` measures the report's own text bytes. The
  two answer different questions (stored noun vs. produced document) and
  are documented rather than unified.

### 10.5 Idempotency and delivery robustness — at parity

Repeated or reordered delivery leaves both the job and the emitted event
stream exactly as the single-delivery case left them.

- **Submit**: an id names one run. An active id is rejected and left
  undisturbed; a **terminal** id is rejected too — `a result for this id
  already exists; delete it first` — rather than silently replacing a
  result the caller may not have read. Delete-then-submit is the explicit
  path (there is no replace flag; adding one would be a wire change). A
  retried submit never schedules a second timer.
- **Wake**: a timer for a deleted, cancelled, or completed job emits
  nothing and leaves the job byte-identical.
- **`%writ`**: the wire is `[%job id %load <generation> <tag> ~]`, where
  the generation is the job's submit time. A response is absorbed only if
  it is for a known, unsealed job, of the right generation, holding that
  tag. So a response left over from an earlier job that held the same id,
  a duplicate, one for a superseded load, and one for a tag already
  satisfied are all dropped — and, critically, dropped **without a
  step**, so a stale delivery cannot spend a slice or schedule a second
  timer. Responses are absorbed by tag, so the order Clay answers in
  cannot change the run.
- **Unrecognised load wire**: an in-flight read whose wire shape predates
  this engine is ignored rather than crashing the event.
- **Cancel/delete**: cancel seals a job at any stage, including one paused
  on Clay; cancel of an unknown or terminal id is a no-op; delete requires
  a terminal job, frees its quota, and a second delete is a no-op.
- **Watcher reconnect**: rejoining after the end gives exactly the terminal
  result with no partial-stage replay; mid-run it gives the stage and
  progress the job is actually at.

One residual sharp edge, recorded: the generation is the job's submit time,
so two runs of the same id created in the same Arvo instant would share
one. Reaching that requires submit, cancel, delete, and resubmit to land in
a single instant, and the intervening delete is what makes the id reusable
at all; a monotonic counter would need a state field (unit 10.6).

### 10.6 API versioning and state migration — at parity

**The public API now carries a revision.** `sur/tla-lus` exports
`api-version`, and `/x/version` returns `[api state]` so a caller can tell
what it is talking to.

| revision | what changed |
|---|---|
| 1 | the unit-2 frozen wire |
| 2 | a `%clay` bundle's `root` is a **module name** (it was a path); `source-ref`/`read-request`/`read-response` exist; `step-result` gained `%await` |

The `action` and `update` shells are unchanged — no caller-visible change
required a bump there. The `on-peek` `$job` projection and the artifact
scry shape are untouched.

**State is `%3`** (`job-3`). The record's fields are the same as `%2`; what
moved under it is the request's source bundle. `jobs-2-to-3` carries
terminal jobs over whole (submit time, statistics, artifacts, diagnostics)
and seals an active job `%failed 'restarted: the source-load stage is new;
resubmit'` — its continuation predates the `%modules` stage and cannot be
resumed honestly across it. (The Work Unit 7.7 contract would catch the
incompatible cursor at the next step anyway; the migration says so up
front.) The async-load cursor lives in the jammed continuation, the pinned
case in the request, and quota accounting is derived, so none of them
needed a field on the job.

Two defects in the old migration path are fixed here, both found by
running it:

- **Historical molds named live types.** `state-1` was defined as
  `(map req-id job)` — the *current* `/sur` `$job`. When unit 10 reshaped
  the `%clay` bundle, every "frozen" mold silently changed with it, so the
  molds no longer described what had actually been stored. They are now
  frozen copies (`source-bundle-2`, `request-2`, `job-1`, `job-2`) in
  `lib/migrate`. *(Historical: R1.5.12b later deleted `lib/migrate` and
  collapsed the pre-`%3` chain — nothing had been released, so there was no
  stored `%0`/`%1`/`%2` state to migrate from. The frozen-copy rule survives
  in `app/tla-lus`'s `versioned-state`; the file does not.)*
- **`on-load` required the stored type to nest.** `!<` type-checks the
  vase as stored, so *any* change to a mold reachable from the state made
  the whole load fail — and the fallback wipes every job, including
  completed results a caller had not collected. `on-load` now coerces the
  noun (`;;`) through the frozen molds, still inside `mule`. A genuinely
  unreadable state still falls back to empty; a merely restyled one no
  longer does.

A pre-unit-10 `%clay` job cannot actually appear in a stored state — the
bundle was typed-rejected at `validate` for the whole life of `%1` and
`%2` — so the root-path-to-module-name conversion is frozen for the type,
not for data anyone has. It converts `/die-hard/tla` to `die-hard`.

### 10.7 Close: what a Clay run is, and what it still is not

`%check`, `%analyze`, and `%simulate` run over `%clay` sources exactly as
they run over an inline bundle. The equivalence is measured, not asserted:
for the same texts, both paths produce the same **result**, `run-stats`,
**diagnostics**, rendered **report**, and typed **counterexample** — a
passing run, an invariant violation with its shortest trace, a deadlock,
and a rejected config are each compared field by field. The only artifact
that legitimately differs is the provenance record, and only in its id
column (`inline/spec` vs `/~zod/tla-lus/287/…/spec/tla`).

**Responsiveness.** A Clay run at budget 1 is a sequence of bounded slices
that interleave loading and checking, and it ends where the unsliced run
ends. A job paused on Clay is cancellable like any other: cancel seals it,
a response arriving afterwards is not absorbed, and stepping the sealed job
changes nothing. No Gall event ever blocks on a read — structurally, not by
convention: the scaffold gate fails if any file under `desk/lib` or
`desk/sur` contains a scry. The dead synchronous `clay-resolver` that
unit 10.0 inventoried was deleted here.

Still not done for Clay sources, each typed-rejected or documented rather
than silently degraded:

| Not supported | Behavior |
|---|---|
| Clay **write-back** (`allow-write`, `%write-translation`) | flag accepted and ignored (unit 13) |
| cfg **source override** (`check-opts.cfg`) | typed rejection |
| PlusCal translate-before-check | typed rejection |
| remote-ship / cross-desk live subscriptions | out of scope; a run reads one pinned revision of one desk |
| a watchdog for a `%writ` that never arrives | a job paused on Clay stays active (reads are answered synchronously when the path does not exist, and the pinned case is settled, so an unanswered read is a Clay bug) |
| listing vendored standard modules in the provenance record | they are not read, and are fixed by the desk revision |
| sharing parsed trees across stages | the loader parses each module once to extract references and discards the tree; a cross-stage cache would put syntax trees into the persisted continuation |

## Unit 6C (C1) — StandardModule operators

Baseline recorded by subunit C1.0 (inventory only; no behavior changed). The
authoritative, generated list of every reachable operator and its
classification is `desk/test-data/stdops/inventory.txt` (131 surfaces: 44
required, 2 body-evaluated, 7 deferred, 78 excluded); the full support matrix
lands with C1.8.

**What evaluates today** (C1.1-C1.6). Forty-seven operator keys, resolved by
`[module operator arity]` as tlc2 binds a Java method — never by bare name:
`Naturals!{+ - * ^ \div % < > \leq \geq ..}` and unary minus at arity 1;
all eight declared `Sequences` operators (`\o Len Head Tail Append SubSeq
SelectSeq Seq`); both `FiniteSets` operators; every overridden `Bags`
operator; the `TLC` module's pure operators (`:>`, `@@`, `Assert`,
`ToString`, `Permutations`, `SortSeq`); and the three non-enumerable set
descriptors `Nat`, `Int`, and `Seq(S)`. SYMMETRY evaluates its definition
through the same registry, so `Permutations` has one implementation.

`Print`, `PrintT`, `TLCGet`, and `TLCSet` are **typed rejections that name
what is missing**, never silent no-ops: the first two write to TLC's console
and this engine has no output channel on the evaluation path; the last two
read and mutate engine state the evaluator does not own. `TLCGet` still
reproduces the pin's EC 2145 for a key TLC itself does not define.

Each override records the pin's **argument contract**: a plain `MethodValue`
receives evaluated arguments, while an `@Evaluation` method receives the
unevaluated node (`TLCEval` and `TLCGet` here) and may pin a `minLevel`.
`minLevel` is carried but not yet observable: TLC uses it to keep a
state-level override out of its constant-folding pass, and this engine has no
such pass. An argument-type failure keeps the pin's error code and names the
operator and argument position; the pin's own message names the Java method
signature, which is normalized away.

`Cardinality` and `IsFiniteSet` take their argument as a lazy *set*, so
`IsFiniteSet(Nat)` is FALSE and `Cardinality(Nat)` is EC 2181 — the infinite
descriptors answer rather than being forced. `\subseteq` is likewise lazy: the
left set is streamed and `SUBSET A \subseteq SUBSET B` is reduced to
`A \subseteq B` (tlc2 `SubsetValue.isSubsetEq`), so neither power set is
materialized — `SUBSET (1..42) \subseteq SUBSET (1..23)` answers instead of
overflowing (R1.5.2). Bag operators accept exactly what
`Value.toFcnRcd` accepts (a function, a tuple, or a record), and their
diagnostics reproduce the pin's text including its quirks: the infix operators
are named `(+)` and `(-)`, and `SetToBag` reports itself as `BagToSet`.

A sequence argument is accepted exactly where TLC accepts one — a tuple, or a
function whose domain is exactly 1..n (`Value.toTuple`) — and the string forms
of `Len`, `Tail`, `SubSeq`, and `\o` behave as the pin does. `SelectSeq` takes
an operator argument, so the evaluator applies it directly under the same
recursion budget, resolving the argument through SANY's `$OpArg` encoding.

**Resolution order** matches `SpecProcessor`: an override beats the
definition's TLA+ body, and only then is a body evaluated. This is not a
preference — the vendored `Naturals.tla` defines `a+b == {a, b}` and
`Nat == { }` as deliberate dummies for tools to override, so evaluating a
standard body TLC overrides would silently produce garbage.

**What is typed-unsupported.** Everything else a spec can reach, including
`Nat`, `Int`, `Seq`, `SubSeq`, `SelectSeq`, `IsFiniteSet`, every `Bags`
operator, and every `TLC` operator (`:>`, `@@`, `Assert`, `ToString`,
`SortSeq`, `Print`, `PrintT`, `TLCGet`, `TLCSet`). The failure names itself —
`unsupported StandardModule operator: Naturals!Nat/0` — and never returns a
value.

**Definitions imported through `EXTENDS` now evaluate** (C1.1, closing the
unit-7 finding). A module's inherited definitions are generated from their own
module and layered under its own, so a local definition shadows an imported
one. The single StandardModule operator the pin does *not* override,
`Bags!SubBag`, therefore binds to its vendored body; evaluating it still needs
recursive functions and multi-binder set constructors (unit-6.5 residue).

**Arithmetic is at the pin's semantics** (C1.2). `\div` floors (Java's `q--`
correction, so `(-7) \div 2 = -4`), `%` requires a **positive** divisor and
returns a non-negative remainder (`(-7) % 3 = 2`), `^` follows `Expt`, and
TLC's integers are 32-bit — `+ - * ^` raise EC 2178
(`Overflow when computing 2147483647+1`) and a numeral above 2^31-1 raises
EC 2265 (`TLC can't handle a number this big.`), which in TLC fails the whole
run and here fails the expression that contains it. `\div` by zero is EC 2179,
`0^0` is EC 2180, and a negative exponent or non-positive `%` divisor is
EC 2169 with the pin's operand text.

`Nat` and `Int` are **non-enumerable set descriptors**, as they are in TLC
(infinite `UserValue`s whose `member` is structural): `3 \in Nat`,
`(-1) \in Nat`, `1..3 \subseteq Nat` all answer, quantifying over them is a
typed failure rather than a hang, and a non-integer membership test raises
EC 2158 with the pin's message.

Error codes are the pin's throughout (2132, 2145, 2154, 2158, 2169, 2176,
2178, 2179, 2180, 2181, 2182, 2183, 2184, 2265, 2266, 2283).

**This is checked, not asserted.** `tests/lib/stdops-diff` (generated) runs
every arity-0 definition of the fixture corpus through the registry and
compares it against the pinned oracle's own projection — **91 definitions,
byte for byte**. A definition this port deliberately answers differently is
named in that arm's skip list with its reason, so a new divergence cannot
appear silently. The complete list of deliberate skips:

| definition | why |
|---|---|
| `Nat`, `Int`, `Seq(S)` in a value position | non-enumerable descriptors here, `UserValue`s at the pin |
| any `SelectSeq`/`SortSeq`/`BagOfAll` with a `LAMBDA` argument | the LAMBDA is now in the semantic graph (R1.3.1: `$OpArg`-encoded anonymous OpDefNode, level via `l-def`); *evaluating* a LAMBDA-parameterized StandardModule operator during model-checking remains deferred (`resolve-oparg`) |
| `1 + "a"` | the pin's message names the Java method signature; normalized here |
| `Bags!SubBag` applied | its vendored body needs recursive functions and multi-binder set constructors (unit-6.5 residue) |
| `Print`, `PrintT`, `Any` | typed rejections here (no output channel; `Any` excluded) |
| the whole `st-string-order` case | family 5, measured and approved (above) |
| the whole `st-big-literal` case | the pin fails the entire load on a numeral above 2^31-1; here the expression containing it fails |

Differences that remain in this area, all failures rather than wrong values:

| case | TLC | here |
|---|---|---|
| `Nat`/`Int` in a value position (`Expr == Nat`, `Cardinality(Nat)`) | a `UserValue` rendering `Nat`; `Cardinality(Nat)` is EC 2181 | typed rejection `unsupported StandardModule operator: Naturals!Nat/0` — there is no UserValue kind |
| `S \cap Nat`, `S \cup Int`, `Seq(Nat)` | evaluated lazily | rejected: set algebra and a descriptor's range take value operands, and the infinite sets are descriptors |
| quantifying over `Nat` | a long non-enumerable-quantifier-bound message naming the bound | `Attempted to enumerate the non-enumerable set Nat.` |
| a non-integer argument to `+ - * ^ \div %` | fails inside the Java `MethodValue` cast, naming the method signature | the same EC (2154) with a normalized message: `The second argument of + should be an integer, but instead it is:` |

**Excluded surfaces** (typed unsupported, by design): `TLCExt`, `Json`,
`Toolbox`, `RealTime`, `Reals`, and the `_*` trace-expression modules;
`TLC!JavaTime` (wall clock) and `TLC!Any` (universal value);
`Randomization` and `TLC!RandomElement` (unit 9 owns TLC's RNG). Java methods
that no StandardModule declares — `Sequences!Cons/Insert/SelectInSeq`, the
`Integers` class's duplicate arithmetic, `Strings`, `AnySet`,
`TransitiveClosure` — are unreachable in TLC too.

**String order (family 5)** remains the approved difference described under
*Unit 9 — Constant evaluation*. C1.0 froze the oracle baseline in
`desk/test-data/stdops/st-string-order/golden-ops.txt`, which shows the
divergence is wider than string sets alone: it also fixes record field order,

## Release R1.4 — recursive function definitions

tlc2 evaluates `f[x \in S] == e(f, x)` to a **lazy `FcnLambdaValue`** and forces a
point only when it is applied. Three consequences were measured at the pin and are
reproduced or recorded here:

**Recursion direction does not matter (reproduced).** Because points are forced on
demand, a body may refer to any other point, not merely an earlier one:
`Fwd[n \in 1..3] == IF n = 3 THEN 0 ELSE Fwd[n + 1] + 1` is `<<2, 1, 0>>` at the pin.
The port has eager values, so `+eval-recfcn` sweeps the domain to a fixpoint — each
unsolved point retried with the self-binder bound to the points solved so far, stopping
when a pass solves nothing new. Every well-founded definition converges regardless of
which direction it recurses.

**The value class is a property of the expression (reproduced).** `R1[n \in 1..3] == …`
is a `FcnLambdaValue` and `NR1 == [n \in 1..3 |-> n]` a `FcnRcdValue`, though both render
as tuples; `R0[n \in 0..2] == n` shows the pairs-vs-tuple rendering is decided by the
*domain*, not the class. The class therefore cannot be read off a value, and
`+kind-of:check` reads it off the semantic node instead.

**A circular definition — approved difference.** `Circ[n \in 1..2] == Circ[n] + 1` does
not fail in tlc2: it returns the unforced lambda, printed as
`[n \in 1..2 |-> <expression line 7, col 21 to line 7, col 31 of module A>]`. That form
has no analogue here — the port has no unforced-value representation, and reproducing it
would mean carrying source spans inside values. A definition that cannot progress reports
the failure its last sweep produced. No corpus case depends on this.

## Release R1.4 — multi-binder constructors

**Print order of a multi-binder function — approved difference.** tlc2 leaves a
multi-binder `FcnRcdValue` un-normalized when printing, so
`G == [i \in 1..2, j \in 1..2 |-> i * 10 + j]` comes out in *construction* order,
first index fastest:

```
G     FcnRcdValue  (<<1, 1>> :> 11 @@ <<2, 1>> :> 21 @@ <<1, 2>> :> 12 @@ <<2, 2>> :> 22)
GDom  SetEnumValue {<<1, 1>>, <<1, 2>>, <<2, 1>>, <<2, 2>>}
```

`DOMAIN G` is sorted while `G` is not, which is how one can tell. The port normalizes
function pairs into its storage order (sorted by domain point), and that ordering is
load-bearing — value equality and state fingerprints depend on it. Matching tlc2's print
order would mean either abandoning the normal form or carrying insertion order inside
`vfcn`, a mold `lib/config`'s `cfg-value` and the jammed state share. The pairs are
identical and the function is the same function: `G[1, 2]` is `12` and `DOMAIN G` agrees
byte-for-byte. This belongs to the same family as the other value-order differences.

**Tuple-pattern quantifier binders — not supported.** `\E <<i, j>> \in S : P` is
rejected. The semantic graph binds a tuple binder's identifiers individually
(`+qbound-vars`) and `+$ sem-bound` carries no destructuring flag, so this shape is
indistinguishable from `\E i, j \in S : P`, which means something different — the first
destructures one element of `S`, the second ranges each variable over all of `S`. Tuple
binders *are* supported in definitions, `$SubsetOf` and `$SetOfAll` (R1.3.3.2/R1.3.4);
quantifiers need the flag added to `sem-bound` first.

## Release R1.4 — evaluator diagnostics

**Decimal (Real) literals — same rejection, different moment.** tlc2 rejects a decimal
literal while *processing the spec*, before any evaluation, and the failure takes the
whole module down: `TLCRuntimeException: TLC can't handle real numbers. 1.5`. Because
it is a `TLCRuntimeException` and not an `EvalException` it carries **no error code**.
The port rejects at evaluation instead, with the pin's wording and likewise no code, so
a spec using Reals is refused either way — the difference is *when*, not *whether*.
`Reals` remains an excluded surface.

**Record field selection — message text not reproduced.** `[a |-> 1].b` raises a
`TLCDetailedRuntimeException` whose message embeds a source span: `Attempted to select
nonexistent field "b" from the record [a |-> 1] line 7, col 11 to line 7, col 21 of
module A`. The port's `+apply` operates on values, not semantic nodes, so the span is
not available where the message is built; the failure is still typed and still refuses
the expression. The four *function*-application wordings are reproduced exactly,
including tlc2's split between an inline `[i \in 1..3 |-> i][9]` (`In applying the
function …`) and a definition's `F[9]` (`Attempted to apply function: …`), which differ
because tlc2 keeps the former a lazy `FcnLambdaValue` and normalizes the latter to a
`FcnRcdValue`.

## Release R1.4 — `TLC!Print` and `TLC!PrintT`

**Decided in R1.4.6: approved difference, a typed rejection.** In tlc2 `Print(out, val)`
returns `val` and writes `out` to the console, and `PrintT(out)` returns `TRUE`. The
values are trivial and deterministic — only the console write is missing here, because
Gall owns effects and the evaluator is a pure function with no output channel.

The port refuses the expression, naming what is absent:
`unsupported StandardModule operator: TLC!Print; it writes to the TLC console and this
engine has no output channel`.

Two alternatives were weighed and rejected. **Returning the value and dropping the
output** is closest to tlc2's value semantics and would let a spec that uses `Print` for
debugging run rather than fail — but a silent no-op is exactly what plan-2 invariant 8
forbids. **Routing the output to a job artifact** is the honest analogue, since the job
kernel already produces artifacts, but `+eval` would have to carry an accumulator through
every return — roughly a hundred evaluator arms, surviving the recursive-function fixpoint
sweeps and the lazy set cursors — which is a change to the evaluator's calling convention
rather than a feature. That option remains open and is now costed.

The consequence to be aware of: **a spec using `Print` is refused here where tlc2 runs
it.** Reversing the decision is a small change to `+print-op` and the affected goldens.

### What measuring `-view` turned up

`-view` is *not* a command-line VIEW override, which is what R1.8.0's inventory
had guessed. It sets `TLCGlobals.useView`, which makes `TLCStateMut.toString()`
render the VIEW's value instead of the bindings. Chasing that down surfaced a
real defect one level below:

**`VIEW` and `ALIAS` were parsed, validated, carried in the `run-spec` — and
silently ignored by every engine path.** Neither `lib/job` nor `lib/check` ever
read those fields. That is not cosmetic: tlc2 fingerprints the **VIEW's value**
(`TLCStateMutExt.fingerPrint`, line 262ff), so dropping a VIEW makes the port
report *more distinct states* than tlc2 and can change whether a run terminates
at all.

Two changes, in the release's standing doctrine that an unsupported option is
refused or documented, never silently degraded:

- **`VIEW` is now validated exactly as `Spec.getViewSpec` does** — EC 2229 (not
  defined), 2233 (resolves to a constant), 2228 (takes an argument), all with the
  role string `view function`. The port's existing `+ck-action` already produced
  those three codes and message bodies for INIT/NEXT.
- **Both are then typed rejections** at `%config` (kernel) and in `search-ctx`
  (console), naming what is missing.

`ALIAS` is deliberately **not** validated. `Spec.getAliasSpec` runs only when a
trace is printed, so an undefined `ALIAS` is `ok` at config time — measured
against the pin, and `val-alias-undef` asserts exactly that so a later "symmetry"
cleanup cannot over-validate it. That asymmetry between VIEW and ALIAS is real
and now pinned.

VIEW-based fingerprinting and ALIAS trace rendering remain unimplemented; they
are now honest refusals rather than wrong answers.

**R1.8.8's full-suite run proved the point.** `Github746` — a tier-2 safety-batch
spec whose `.cfg` carries `ALIAS Alias` — had been *agreeing* with TLC. It agreed
on the verdict, the counts and the depth, and disagreed on every state line
underneath: TLC renders the violating initial state through the alias
(`/\ i = 1 /\ foo = "bar" /\ j = TRUE`) where the port printed the raw binding
`i = 1`. The comparator could not see it, because `tlc_projection` captures trace
lines only after the two counter-example markers, and an initial-state violation
is announced by neither. The typed rejection is what surfaced it. It is now
censused (safety batch: 13/14 agree, 1 listed), which is the honest state — a
silently wrong trace was traded for a visible refusal.

## Release R1.8.3 — the job kernel's report is the console path's — at parity

R1.8.0's audit found `cfg-runspec`'s one named residue had a twin at the same
call site; R1.8.2 found a third symptom of the same defect. All three came from

## Release R1.8.2 — the last three `cfg-validate` residues — at parity

R1.8.1.3b left three narrow residues. R1.8.2 closed all three, and the third one
turned out to be smaller than its own residue text claimed.

**Per-module substitutions are validated.** `+mod-subst`/`+one-module` run the
2223/2224/2225/2226 loop over each module's `mod!lhs <- rhs` table, then
`+unknown-modules` raises TLC_NO_MODULES (2245) for a config module name the
specification does not define — `SpecProcessor.java:711-770`, in the Java's
position: after the root 2226 sweep and before `processConstantDefns`. It is not
simply the root loop repeated; three asymmetries are explicit in the Java and
reproduced here:

- the **2223** self-reference test is against *this module's* table
  (`mDefs.containsKey(rhs)`), not the root's `overrides`;
- the **rhs still resolves in the root `defns` table** — the Java says so in a
  comment, "The rhs comes from the root module" — so a per-module override may
  name a root definition and nothing else;
- **2225 fires here for every operator**, where the root loop defers a declared
  constant's arity check to `processConstantDefns`.

What made this residue real was the missing input, not the loop: the port's graph
exposed the root module plus its `EXTENDS` imports, never a *non-root* module's
own operator list. `sem-module` now carries `modops` (`+mod-opdefs`), every module
in the spec mapped to the names and arities its own `ModuleNode.getOpDefs()`
exposes — the EXTENDS closure first, first definer winning and LOCALs not
exported, then the module's own definitions, whose LOCALs are in the module and so
are listed. Its key set is also the `modSet` the 2245 check tests against.

**EC 2230 renders an operator record.** `+render-oprcd` is `OpRcdValue.toString()`
(`OpRcdValue.java:247`): `{ ` then one `<arg, arg, val>` record per config line
joined by `, `, then `}` with no space before it; an empty record is `{ }`.
`addLine` appends and never dedups, so the config's line order *is* the rendering
order. Measured against the pin: `F(1) = 2` with `F(3) = 4` renders
`{ <1, 2>, <3, 4>}`.

**EC 2281's temporal addendum — and a correction.** A substituting body that is
non-constant because it is *temporal* throws EC 2261
(`TLC_ENCOUNTERED_FORMULA_IN_PREDICATE`, `Tool.java:2808-2846`) rather than EC
2280, and 2281's addendum carries that message. The residue text had said tlc2
renders it with "its abbreviated expression rendering" — **it does not.**
`SemanticNode.toString()` returns `getLocation().toString()` unless the
`SemanticNode.showPlainFormulae` system property is set, which no default run
sets. So the message's second parameter is a *location*, which `+loc-str` already
produced for the 2280 case, and the whole residue was one message template and one
walk result away.

`+nonconst-ref` now returns a typed `ncref` — `%ident` (2280) or `%temporal`
(2261) — and stops at a temporal node **without descending into it**, because
`Tool.evalImpl` switches on a node's OPCODE before evaluating its arguments. So
`C <- []P` names the box, never P's contents. The eight labels are the ones
`Tool.java` passes as the message's first parameter: `[]A`, `<>A`, `WF`, `SF`,
`\EE`, `\AA`, `a ~> b`, `a -+-> formula`.

The `cfg-val` corpus went 27 -> 35: one case per per-module code (2223, 2224,
2225, 2226, 2245) plus a valid per-module override, an operator-record 2230 body,
and a temporal 2281 addendum. All green, and `check-opt-cfg` — which owned no
residue of its own, only these three through `lib/config` — reaches `parity` with
this row.


## Release R1.8.1 — the tier-2 liveness batch, and what it measured

R1.8.1.4 wired the TLC **liveness** batch that had been deferred since R1.1.8 and re-deferred by
R1.5.7: nine flat single-file `test-model` specs with a temporal `PROPERTY`, run through
`check:check` and compared to the pinned TLC verdict + distinct-count. **Three of nine agree.**
The six that do not are frozen in `desk/test-data/tier2/divergences.txt` and **asserted** by the

passing unnoticed.

Two of them were closed on the way, and both were invisible to the existing fixtures:

- **The liveness graph build dropped the model CONSTRAINT.** All six liveness graph builds in
  `lib/check` passed `~` for `CONSTRAINT`/`ACTION_CONSTRAINT` where the safety and implied-action
  paths pass them. tlc2 never enqueues a constrained state, so its liveness runs over the
  constrained graph; the port's ran over the unconstrained one, and a spec whose state space is
  finite only under its constraint did not terminate. Fixed, along with a second bug it exposed:
  `+succ-fps:liveness` returned the raw next-state relation while its callers did
  `~(got by states)` on each successor — safe while the graph is closed under that relation, fatal
  once it is pruned. `+succ-fps` now drops successors absent from the graph, which is what a
  constrained edge is. Neither bug is reachable without a `CONSTRAINT`, and no `mc` or `liveness`
  fixture has one.
- **The comparator was reading the wrong line.** `+tlc-sum` took the first line of the run's output
  as the verdict, where the Java side of the same comparator selects the `Model checking completed`
  / `Error:` line. No safety spec prints anything before its verdict; R1.8.1.2's EC 2255 warning is
  the first that does, and it made a passing spec read as a divergence.

The six remaining divergences are **liveness-engine** behavior, not config decomposition — five
bail `%tlc-live-wrong-formula-format` (tlc2's EC 2214) in `+class-default:temporal` on formulas
tlc2 handles, and one is a deadlock-vs-liveness precedence difference on the same state count.
`Github1389` names the missing mechanism: it is upstream's regression test for RECURSIVE operators
with temporal bodies, which `Liveness.astToLive` expands during tableau construction. That is why
`tlc-live-normalize` moved from `approved-difference` to `partial` — a terminal row that bails on
in-scope specs was overstated, and only running real specs could show it.

## Release R1.6 — stuttering in the product graph

**Approved difference, measured in R1.6.3.** TLA+ behaviors may always stutter, and the port and
tlc2 grant that in different places. tlc2's exhaustive behavior-graph product contains only the
real successors (`LiveCheck.LiveChecker.addNextState`) and allows stuttering inside the acceptance
search; the port adds a **self-loop on every product node** and lets the ordinary SCC search find
it. The two are verdict-equivalent across the whole liveness corpus — removing the port's edge
turns `wf-absent-viol` and `diamond-const-false` from `violated-property` / `CLASS stuttering` into
`ok`, so it is exactly what carries stuttering there.

The `PRODUCT` differential therefore excludes these edges *structurally*, not by shape: `pedge`
carries a `stut` tag and the projection drops tagged edges only, so a genuine `x' = x` transition
is still compared. A "skip self-loops" filter would have hidden real ones.

Note what this is **not**. The stutter successor used to be crossed with the tableau successors,
which discovered product nodes that neither tlc2 nor the port's own `+build-product` count path
had. That was a defect, not a difference, and R1.6.3 fixed it: the stutter edge is now a pure
self-loop on `(fp, tidx)` and discovers nothing. Its own path (`LiveCheck.checkTrace`) does add a
stutter successor for a simulated behavior, and the port matches that.

## Release R1.2 — bails where tlc2 raises a typed diagnostic

**Approved difference, audited in R1.2.7.** Sixteen `!!` sites remain in production-reachable port
code. Every one is labelled, and every one has an argument recorded beside it; they fall into two
classes.

**Unreachable by construction (13).** `+st-pred-bool` and `+cs-eval` refuse anything above state
level, and `+ca-eval` anything above action level, because the entries they are given are filtered
to those levels first — `+state-preds-of` keeps `le-level <= 1` exactly as `TBGraphNode`'s
constructor does, and `+classify` bins `[]<>S` into checkState only when its level is `<= 1`.
Reaching one is an invariant violation, not an input shape. The same holds for
`+render-value:config` (`+parse-cfg` produces only the five value shapes it renders),
`+job`'s unplanned-stage (the stage plan is built, not supplied) and `+diagnostics`' unmapped-EC
(now 45 codes mapped, R1.2.6).

**tlc2's own typed failure, rendered as a bail (3).** `%tlc-live-encountered-actions`
(EC 2249), `%tlc-live-wrong-formula-format` (EC 2214) and `%tlc-live-cannot-eval-formula`
(EC 2251, `LNAll.eval`/`LNEven.eval`) are places where **tlc2 also fails** — it raises the numbered
diagnostic and aborts the run. The difference is mechanism, not outcome: these arms return a bare
`?` or a `par`, so the port has no channel for a typed rejection there and bails instead. The same
input is refused by both; only the rendering differs. Giving them a channel means threading an
`(each … aerr)` through `+consistent-at`, `+cs-bits`, `+ca-bits`, the product build and the SCC
search — a calling-convention change, not a feature, and it is costed here rather than done.
