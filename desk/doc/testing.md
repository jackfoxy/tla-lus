# Testing & Compatibility Validation

`%tla-lus` is validated by **differential testing** against the Java TLA+
toolchain at a pinned commit: every Hoon component is compared, output for
output, with the corresponding Java tool. The comparison is organized into
three tiers.

## The oracle and the pin

All goldens come from `tla2tools.jar` built from the pinned commits
(`tlaplus@4ba7d8811`, `tlaplus-Examples@47b0e2cc`, `vscode-tlaplus@acc095d6`;
see `port-map.md` §0). Both `tools/validate.py` and
`test-data/oracle/regen.sh` refuse to (re)generate goldens if the checkout is
off-pin, so a golden can never silently drift to a newer tool version.

Rule: **never weaken a golden without first proving the Java behavior from the
pin.** Any intentional divergence is recorded in `compatibility.md`.

## Tier 1 — every change (fast, local)

Two halves, both required to be green:

1. **Golden reproducibility** — `python3 tools/validate.py --check`
   recompiles the oracle dumpers (`tools/oracle/*.java`), reruns every
   generator, and hashes the oracle-derived trees before/after to prove they
   reproduce byte-identically from the pinned oracle. Covered generators and
   counts: lexer (249), parser (249), BNF manifest (35 productions), module
   resolution (13), semantic graph + levels (19), constant evaluation (37),
   safety+liveness model checking (5), and the unit-0 oracle baseline (14).
2. **Hoon differential + property tests** — on the fake ship:
   `-test /=tla-lus=/tests ~`. This runs the generated differential shards
   (lexer/parser/sem/modres/eval/mc against their goldens) plus the
   hand-written property suites: `crc` (CRC-32 vectors), `sim` (seeded
   simulation reproducibility/limits), `job` (the resumable engine +
   real-pipeline integration), `bnf` (grammar-manifest drift), `diagnostics`,
   `migrate`, and the `app` agent tests.

Oracle dumpers, by stage: `TokenDump` (lexer), `AstDump` (parser CST),
`SemDump` (semantic graph + levels), `CrcVec` (PlusCal checksums), and the
REPL/TLC/SANY invocations driven directly by the generators.

## Tier 2 — CI / nightly (broader, slower)

Tier 2 is a **separate runner** from tier 1: `python3 tools/tier2.py` (tier 1's
`validate.py` stays fast enough for every change; tier 2 runs TLC over many
specs and belongs in CI/nightly). It owns its own goldens under
`desk/test-data/tier2/`, regenerated by `tools/gen-tier2-tests.py`.

The corpora:

- The `tlaplus/test-model` corpus (175 specs).
- The `tlaplus-Examples` matrix, classified from the repo's own machine-readable
  `manifest.json`s (per-model expected result / distinct-state / depth).
- (Planned) adapted non-UI parser fixtures from the Toolbox and the VS Code
  extension for tagged TLC messages, diagnostics, progress, coverage,
  checkpoints, structured values, stuttering, and lasso traces.

**Classification.** `gen-tier2-tests.py` classifies every module of both corpora
into `desk/test-data/tier2/inventory.txt` — `sany` (parse/semantic in scope),
`check` (SANY + TLC, EXTENDS only the parity-ported operator modules Naturals /
Integers / Sequences / FiniteSets / Bags / TLC), or `excluded:<reason>`
(`pluscal`, `feature:action composition`, `proof`, `module:<unresolved>` for
community/extended modules, or `check-excluded:<mod>` for a model that pulls in
an excluded-operator module). The rules are total, so an upstream-added spec
lands in a bucket and drifts the frozen inventory — which `tier2.py --check`
catches (the drift guard).

**Oracle projection.** For a curated, self-contained subset the generator
captures a normalized Java projection (`desk/test-data/tier2/oracle/<name>.txt`):
a SANY `accept`/`reject` verdict and, where the spec has a model, a TLC verdict +
`STATES gen distinct queue` + `DEPTH` + normalized trace. Header/footer noise
(version, seed, pid, timestamps, temp paths, GC warning, runtime) is stripped;
TLC runs in an isolated temp dir with `-noGenerateSpecTE`/`-metadir` so its trace
spec and state metadata never touch the pinned checkout. `tier2.py --check`
proves the inventory + curated oracle reproduce byte-identically from the pins.

The endpoint: each in-scope spec run through **both** SANY implementations (Java
and the Hoon units 4–7) and, where it has a config, through **both** TLC and the
Hoon checker (units 10–11), comparing pass/fail category, diagnostic codes/spans,
semantic trees, verdict, state counts, depth, and normalized traces.

**SANY comparator (R1.1.1).** `gen-tier2-tests.py` emits `desk/tests/lib/tier2.hoon`
— a Hoon shard that runs each curated spec through `+sany-verdict:semantic` (the
analyze pipeline's accept/reject, matching SANY's console verdict) and compares
it to the pinned Java SANY verdict. It runs on the ship
(`-test /=tla-lus=/tests/lib/tier2 ~`). Specs whose Hoon verdict disagrees with
Java are recorded in `desk/test-data/tier2/divergences.txt` with a reason — not
tested green, but census-tracked so a new divergence cannot appear silently. The
two current divergences (`IllegalOperatorTest` — a higher-order operator-argument
arity edge; `CigaretteSmokers` — `LAMBDA` not in the WU3 graph) are front-end
residues owned by R1.3.

**TLC comparator (R1.1.2).** For each curated safety spec the shard runs
`check:check` and compares the **verdict line + distinct/queue counts** to the
pinned TLC run (the `generated` counter is dropped — it has a safety-stats
off-by-one nuance — and trace labels/depth are a safety `partial` residue, both
compared in a later increment). `DieHard` (a safety violation, 54 distinct) is
green; `HourClock` and `TCommit` are recorded as divergences — both hit the
`x \in S` nondeterministic-assignment residue (the Hoon solver errors
`variable is unassigned`), owned by R1.5.

**Batch scale-up (R1.1.3/4).** `test-sany-batch` is one **`mule`-isolated** arm
that runs the whole flat in-scope test-model batch (**142 specs** — all sizes and
multi-file closures, R1.1.4 having dropped R1.1.3's single-file / < 1.8 KB seed)
through `+sany-verdict` — a crash becomes a recorded outcome, not a test abort —
and asserts the sorted list of modules whose Hoon verdict disagrees with Java
equals a frozen census. Result: **140/142 agree**; both divergences are the
documented front-end (R1.3) residues — `IllegalOperatorTest` (higher-order op-arg
edge) and `BagsTest` (`BagOfAll(LAMBDA …)`, LAMBDA not in the WU3 graph). This is
the slow tier-2 element (~7.5 min); it belongs to the nightly runner, not
every-change tier 1.

**TLC batch (R1.1.5).** `test-tlc-batch` is the checker analogue: one
`mule`-isolated arm runs 14 clean single-file test-model **safety** specs (ok /
invariant-violated / deadlock, small state) through `check:check` and compares
each `[verdict, distinct]` to the pinned TLC run, censusing divergences with the
Hoon verdict inline. Result: **4/14 agree** — a sharp contrast to SANY's 140/142.
The 10 divergences map the checker's real-spec gaps: **7 are the `x \in S` /
`x' \in S` nondeterministic-assignment residue** (`variable is unassigned`),
plus `AssignmentNext` (Hoon deadlocks where TLC completes), `SubsetEq` (Hoon
eagerly enumerates `SUBSET`), and `ConstantOperatorConfiguration` (a cfg CONSTANT
operator override not applied) — all owned by **R1.5**. The census is the point:
tier 2 hands R1.5 a concrete target list.

**Trace + depth comparison (R1.1.R1).** The comparator was `[verdict,
distinct-counts]` while the goldens had carried `DEPTH` and the whole labelled
`TRACE` since R1.1.0 — `DieHard.txt` is 41 lines, 35 of them a seven-state
counterexample. `+tlc-sum` now compares the **whole projection**: verdict, the
distinct/queue counts, the search-depth line, and every trace line (state
headers with their per-action `getActions` labels, and every binding). Both
batches were re-frozen against it, and it found three real divergences where a
count could not:

1. **No `/\ ` conjunct prefix.** `TLCStateMut.toString` renders a single
   variable bare (`x = 0`) and two or more as a conjunct list (`/\ x = 0`); the
   port always rendered bare. Invisible to tier 1, whose only multi-variable mc
   case (`twobit`) has no violation and therefore no trace. **Fixed.**
2. **The unnamed action prints `Action`, not `Next`.** A next-state relation
   that comes from a `SPECIFICATION` has no `OpDefNode`, so `Action.isNamed()`
   is false and `getLocation` prints its generic `"Action"`
   (`Action.java:100-107`); the port labelled it `Next`. `sctx` now carries the
   root action name (`aname`) — the NEXT operator's name in INIT/NEXT mode,
   `Action` under a SPECIFICATION. **Fixed**; it was the whole of the safety
   batch's remaining divergence (`DepthFirstErrorTrace`,
   `TraceWithLargeSetOfInitialStatesTest`), now **14/14 on the full trace**.
3. **`Github710d`:** after a deadlock tlc2 *still* reports the violated temporal
   property and its counter-example, before the statistics; the port's R1.6.6
   pre-emption emits the deadlock report alone. Same verdict, a missing second
   block — censused and owned by R1.6, leaving the liveness batch **8/9**.

Two projections are deliberately normalized, each measured rather than assumed.
The **generated** count stays dropped: R1.1.R0 measured it still diverging on
`DieHard` (253 vs 252) and `Continue` (4 vs 3), so `+drop-gen` is a named
two-spec residue, not a stale workaround. And each state's **bindings are
sorted** on both sides, because tlc2 prints them in `java.util.Hashtable` bucket
order — an approved difference argued in `compatibility.md`.

**Subdir batch (R1.1.6–R1.1.9, completed R1.1.R2).**
`desk/tests/lib/tier2-sub.hoon` runs **every in-scope test-model subdir spec
whose module closure resolves — all 310** — through `+sany-verdict` in chunked
`mule`-isolated arms. A spec's identity is its relative **path** (root module
names collide across subdirs), and the embedded closure is emitted in sorted
module order so the shard is byte-reproducible. Result: **310/310 agree**; the
census is empty (R1.3 closed the last front-end divergence). Combined SANY
coverage is **452/452** embedded test-model specs (142 flat + 310 subdir).

R1.1.6–.9 raised the closure cap 1.5 KB → 4 → 8 → 16 KB and stopped there, and
this document, the generator NB and the R1.1.9 row all then said the 15 specs
above 16 KB were "past the embedding limit" and "would need Clay-read, which the
ship's test framework cannot do". **That was never measured, and R1.1.R0
measured it false.** The 15 alone embed as a 476 598-byte single-arm shard that
builds and runs OK in 365 s; all 310 embed as a **1 338 467-byte** 6-arm shard
that builds and comes back `ok=%.y` in 1 683 s. The largest single closure,
`suite/test211`, is **63 594** raw bytes in one module (66 390 escaped). Nothing
failed per-file, per-arm or per-build.

What the 15 actually cost is **time** — ~24 s/spec against ~4 s/spec averaged
over the 310 — so `SUBDIR_CLOSURE_MAX` is now **70 000**, above every in-scope
spec at the pin, and it exists to bound what a future upstream spec can add to a
nightly arm rather than to mark a wall. No Clay-read harness is needed, and none
should be built for this.

## Close-out gates, and why they are their own unit (R1.8.8)

A unit runs the shards it touched. That discipline is right — it keeps
increments fast — but it is structurally blind to two things, and R1 has now
been bitten by both:

- **Cross-shard breakage.** R1.1.R1 changed `+render-state`'s arity and re-ran
  every shard judged touched; `tests/lib/stream.hoon` also called it and failed
  to *build*. Only the full suite saw it.
- **A gate nobody runs.** R1.5.12b deliberately deleted the pre-`%3` migration
  chain (nothing had been released, so it was collapsed rather than carried) but
  did not update `scaffold-gate.sh` gate 6, which still required
  `jobs-0-to-1`/`jobs-1-to-2`/`jobs-2-to-3`. The gate went **red on 2026-08-17
  and stayed red through nine units** — R1.6, R1.7, R1.1.R0–R4, R1.8.0–.6 —
  because none of them ran it. R1.8.8 found it. The code was right; the gate was
  stale, and it now checks the mechanism the design guarantees (a version-tagged
  union, an `on-load` that *coerces* rather than nests, a `?-` dispatch, and a
  state mold matching the script's own `DESK_STATE`) instead of one historical
  chain.

So a close-out unit runs, in this order:

| | command | proves |
|---|---|---|
| tier 1 | `python3 tools/validate.py --check` | every golden reproduces byte-identically from the pin |
| tier 2 | `python3 tools/tier2.py --check` | inventory + curated oracle + comparator shards reproduce, census asserted exactly |
| ledger | `python3 tools/check-parity.py` | well-formed, and how much is still owed |
| gate | `bash tools/scaffold-gate.sh` | scaffold hygiene, 11 gates (runs tier 1 as its gate 2) |
| release | `bash tools/release-gate.sh` | **fails by design for the whole of R2** — see below. The real gate (R1.9.3): the scaffold gate **plus** ledger closure, tier 2, no stubs, refusals documented both ways, upgrade/restart, reproducible artifacts |
| acceptance | `python3 tools/r1-acceptance.py --suite-log <captured suite output>` | R1's acceptance sentence, **computed** (R1.9.4): ledger closed, docs coherent, release gate green, ship suite green. The suite clause is evidence the caller supplies — omitting it FAILS the clause rather than skipping it |
| suite | `-test /=tla-lus=/tests ~` on the ship | `ok=%.y` — the only thing that sees cross-shard breakage |

A gate that never runs is not a gate. It is a claim.

**A gate that fails on purpose needs saying so, too.** R2.0 re-opened the parity
ledger — R2 brings excluded capability into scope and withdraws approval from
six differences — so `release-gate.sh` gate R1 (ledger closed) and
`r1-acceptance.py` both fail for the whole of R2. That is the intended state.
The failure mode this guards against is someone "fixing" the gate: **do not edit
`r1-acceptance.py` to pass.** It is the record of what R1 proved, asserted
against R1's closing state; R2 gets its own `r2-acceptance.py` at R2.9. A red
gate mid-R2 reads as "R2 in progress", and the number to watch is the owed count
in `check-parity.py`, which should fall monotonically toward zero.

**And the suite earns its slot every time.** R1.8.8's run failed one arm,
`tier2/test-tlc-batch`, on `Github746` — a spec whose `.cfg` carries `ALIAS`.
R1.8.6 had turned the silent ALIAS no-op into a typed rejection, so the first
reading was "the close-out broke a passing spec". It had not: TLC renders that
spec's violating initial state *through the alias*, the port had been printing
the raw binding, and the comparator could not see the difference because
`tlc_projection` captures trace lines only after the two counter-example markers
— and an initial-state violation prints neither. The spec agreed on
`[verdict, counts, depth]` and disagreed on every line beneath. Censused, not
silenced: the safety batch now reads 13/14 agree, 1 listed.

The lesson generalizes past this one spec: **a projection that does not look at
something cannot report it as agreeing.** The dropped generated-count is a
deliberate, documented normalization; the dropped alias-rendered initial state
was an accident nobody had written down. When a differential passes, it is worth
knowing which of the two it is.

## Tier 3 — a performance harness, and deliberately not part of R1

Tier 3 was scoped as "broader `tlaplus-Examples` coverage and bounded
performance models (queue / evaluator / enumeration / fingerprinting / safety /
liveness hot paths)". **R1.1.R3 decided it is out of scope for R1, and it is a
decision rather than another deferral.** The reasoning, so a later reader does
not have to reconstruct it:

**It measures the port against itself, not against Java.** Every other tier here
is a *differential*: a Hoon result is compared to a pinned Java result, and the
verdict is agree / disagree. A performance model has no Java answer to compare
to — the interesting quantity is this implementation's time and space on a
workload, tracked over its own history. That is a different discipline with
different tooling (a baseline store, a noise model, a regression threshold) and
its own failure modes, of which the worst is a flaky gate that everyone learns
to ignore.

**R1's definition of done is a parity statement, and it is now computed rather
than declared.** `tools/r1-acceptance.py` (R1.9.4) evaluates the acceptance
sentence clause by clause and prints `R1 ACCEPTED` only when all four hold.
R1.9 asserts closure over the parity work: every in-scope ledger row `parity`
or a tested `approved-difference`, every differential green and
byte-reproducible. Tier 3
cannot contribute evidence to that statement, and holding R1 open for a harness
that answers a different question would only make the parity claim later without
making it stronger.

**Its measurement substrate is not stable enough to baseline yet.** The port is
still changing shape where it would be measured — R1.1.R2 alone moved a nightly
SANY arm by ~365 s by embedding 15 more specs, and the checker's own cost model
(`live-graph-cap`, `+expand-cap`, `fuel:eenv`) is tuned per increment. Baselines
taken now would be re-baselined repeatedly, which teaches a team to re-baseline
on failure — the exact habit a performance gate must not create.

**What tier 3 would still be worth, later.** The broader `tlaplus-Examples`
coverage half is real differential value and is *not* blocked by any of the
above; it is simply more of what tier 2 already does, gated by nightly runtime
rather than by capability. The performance half wants a spec-shaped workload set,
a stored baseline per pinned runtime, and a threshold wide enough to survive
ordinary variance. Neither is scheduled here.

**Where it lives now.** Future work, tracked in `R1-release-work-breakdown.md`,
not as an R1 deferral. Nothing in tiers 1 and 2 depends on it.

## Fuzzing

`tests/lib/fuzz.hoon` drives the lexer and parser with seeded random
inputs and asserts they never crash — they must return a clean accept/reject,
never bail. Any reduced mismatch discovered by fuzzing is saved as a
regression fixture under the appropriate `test-data/` corpus so it becomes a
permanent tier-1 case.

### The runner and its four outcomes

`+fz-run` (R1.2.1) drives a seeded generator into a **stage adapter** and
classifies every case four ways:

| outcome | meaning | verdict |
|---|---|---|
| `%ok` | the stage produced a result | pass |
| `%rejected` | the stage produced a TYPED rejection | pass |
| `%bailed` | the stage crashed (`mule` caught it) | **failure** |
| `%budget` | the stage hit a work cap instead of finishing | **failure** on this corpus |

`%budget` exists because **`mule` catches a bail but not a loop** — R1.8.1.4
found a liveness build that ran 480 s on a five-state spec. Hoon has no timeout
the harness can impose from outside, so each stage adapter must call its stage
with the caps that stage already has (`live-graph-cap`, `+expand-cap`,
`fuel:eenv`) and report a cap-hit as `%budget`. That is a contract on the
adapter; it cannot be enforced in code, so it is written down here and in the
shard header.

The seed fixes the whole run, so a reported failure replays exactly, and a
failure carries the input that caused it.

### When fuzzing finds a crash

Do **not** fix it in place. In order:

1. Reduce the input by hand (the mutation generators start from valid corpus
   cases, so the distance is usually small).
2. Commit it as a fixture in the corpus that **owns the stage** — a liveness
   crash in `test-data/liveness`, a config crash in `test-data/cfg-val` — so it
   is picked up by that stage's existing generator and comparator and becomes a
   permanent tier-1 case. It does not go in a fuzz-only corpus, which would
   leave it outside every differential.
3. Capture its oracle golden.
4. Only then fix the port.

### Coverage today

Every stage has at least one seeded arm (R1.2 close-out): the lexer and parser
(`+fz-parse`), the semantic graph (`+fz-sem`), config parsing and the whole
`run-spec` path (`+fz-cfg`, `+fz-runspec-*`), the temporal normalizer and
liveness engine and the evaluator through the checker (`+fz-check*`, with
liveness and safety bases), and the decoding of a persisted continuation
(`+fz-kont`). Roughly 1,300 seeded cases per run.

Each arm asserts two things: that nothing bailed or hit a cap, **and** that the
mutations still reached the stage at least N times. The second is not decoration
— an arm that only asserts "no bails" passes trivially when every mutation is
rejected at the parse step and the stage under test never runs.

The gap is not hypothetical. R1.6.0 measured `+ast:temporal` **bailing**
(`%tlc-live-wrong-formula-format`) on five ordinary `test-model` specs, and
R1.2.0 found `<>(x = 1 /\ y = 0)` bailing `%tlc-live-statepred-junction` by
inspection alone. A typed rejection would have been correct in both; a bail is
what this suite exists to forbid.

**When converting a bail, never make it silent**: either prove the site
unreachable and record the argument, or emit a diagnostic that names the shape
that reached it. Two of the port's bail tags already have real tlc2 error codes
behind them (2214, 2249) — a bail with an EC behind it is a diagnostic waiting
to be wired.

## Adding a case

1. Put the source fixture under the matching `test-data/<stage>/` corpus.
2. Run the stage's generator (or `tools/validate.py`) to capture its golden
   from the pinned oracle.
3. Commit the fixture, the golden, and the regenerated shard together.
4. Confirm both tier-1 halves are green.
